# RelationScope V2

RelationScope V2 turns the V1 production classifier into an inspectable ML system with operational telemetry, human feedback, durable batch inference, and explicit model lifecycle management.

The frozen V1 benchmark and promoted model remain unchanged. V2 changes the product and serving/operations layer rather than silently retuning the final test set.

## 1. Word-level relation influence

The ENSAI notebook included attention-score visualizations for the sequence-to-sequence attention model. The production model is a ModernBERT classifier with entity-aware pooling, so V2 does **not** relabel Transformer self-attention as a faithful relation explanation.

Instead, V2 uses relation-specific **word occlusion**:

1. run calibrated open-set inference;
2. select the predicted relation, or an explicitly requested relation ID;
3. group tokenizer subwords back into complete displayed words;
4. mask every complete word independently;
5. evaluate all perturbed inputs in one batch;
6. measure the change in calibrated target-relation probability.

For a word \(w\):

```text
influence(w) = P(target | original) - P(target | w masked)
```

Interpretation:

- positive: masking the word lowers target confidence → the word supports the relation;
- negative: masking the word raises target confidence → the word opposes the relation;
- near zero: little measured effect under this perturbation.

The frontend preserves sentence order and renders this as a signed word influence map. It also surfaces the strongest supporting cues.

This is perturbation-based evidence, **not a causal explanation**.

Endpoint:

```text
POST /v2/relations:explain
```

## 2. Privacy-preserving production telemetry

Every V2 open-set prediction can emit a small operational event containing:

- model version;
- operating profile;
- KNOWN / UNKNOWN decision;
- top confidence;
- threshold;
- inference latency;
- text length;
- SHA-256 digest of the input text.

Raw sentence text and entity strings are not written to telemetry.

Telemetry is stored as JSON objects in the private V2 operations bucket and can be summarized through:

```text
GET /v2/metrics/summary
```

The dashboard reports recent prediction volume, KNOWN/UNKNOWN rate, mean confidence, and p50/p95 inference latency.

The object-per-event design is intentionally simple and appropriate for the low-volume portfolio deployment. A high-throughput production system would normally move this stream to a dedicated analytics/event pipeline.

## 3. Human feedback loop

After a prediction, the UI can record:

- confirm;
- corrected relation;
- mark as unknown;
- skip.

By default, feedback stores only hashes and structured prediction metadata.

Raw sentence text and entity spans are persisted **only** after the user checks the explicit training-data consent option.

A relation catalog endpoint lets the frontend offer corrections from the model's 56 known labels:

```text
GET /v2/relations
```

Consented feedback can later be exported as review/retraining JSONL:

```bash
uv run python scripts/export_feedback_dataset.py \
  artifacts/review/feedback.jsonl \
  --ops-bucket YOUR_OPS_BUCKET
```

Exported feedback is still review data, not automatically trusted ground truth. Human validation remains part of the retraining process.

## 4. Durable asynchronous batch inference

V1 supports one bounded synchronous Transformer batch.

V2 adds durable jobs:

```text
POST /v2/batch-jobs
GET  /v2/batch-jobs/{job_id}
```

Production flow:

```text
public Next.js
      |
      v
private FastAPI
      |
      | create durable input/status objects
      v
private GCS operations bucket
      |
      | enqueue
      v
Cloud Tasks
      |
      | OIDC-authenticated callback
      v
private FastAPI worker route
      |
      | vectorized chunks
      v
ModernBERT
      |
      v
durable result JSON
```

The public Next.js proxy explicitly blocks `/v2/internal/*`. The worker callback is reachable only through the private Cloud Run service and is invoked by the dedicated Cloud Tasks service account.

Local development uses the same durable job format but executes inline when Cloud Tasks environment variables are absent.

## 5. Model registry and promotion

V2 separates three concepts:

```text
training output
      |
      v
immutable registered release
models/releases/<model-version>
      |
      | explicit promotion
      v
production alias
models/current
```

Register a model release:

```bash
uv run python scripts/register_model_release.py \
  artifacts/open_set/best \
  --bucket YOUR_MODEL_BUCKET \
  --model-version modernbert-open-set-v1.1
```

The command refuses to overwrite an existing immutable release unless `--force` is explicitly supplied.

Promote a registered release:

```bash
uv run python scripts/promote_model_release.py \
  --bucket YOUR_MODEL_BUCKET \
  --model-version modernbert-open-set-v1.1
```

Promotion copies the registered bundle to `models/current` and writes an audit event under `models/promotions/`.

The read-only API registry is available at:

```text
GET /v2/models
```

## 6. V2 GCP resources

Terraform adds:

- Cloud Tasks API;
- private operations GCS bucket;
- 90-day operations-object lifecycle by default;
- dedicated Cloud Tasks caller service account;
- Cloud Tasks queue with bounded dispatch rate/concurrency;
- API permission to enqueue tasks;
- task-caller permission to invoke the private API;
- API read/write permission only on the operations bucket;
- 900-second API request timeout for bounded asynchronous worker callbacks.

The existing security boundary remains:

- public: Next.js web service;
- private: FastAPI service;
- browser: no Google service-account token;
- model bucket: API read-only;
- operations bucket: API read/write;
- Cloud Tasks worker endpoint: not exposed through the public proxy.

## 7. Compatibility

All V1 routes remain available.

V2 introduces new routes under `/v2` and does not change the frozen V1 evaluation report.

This means the V1 tag remains a reproducible checkpoint while `main` can evolve toward the V2 product.

## 8. Retraining boundary

V2 implements the **feedback-to-review-data pipeline**, not automatic self-training.

That separation is deliberate:

```text
production feedback
      ↓
consent filter
      ↓
review export
      ↓
human validation
      ↓
retraining experiment
      ↓
evaluation + promotion gates
      ↓
new immutable model release
```

A new model must still pass evaluation and promotion criteria before it becomes production.
